# Live implementation and current proof

EMER uses direct OpenAI `gpt-live-1`, client delegation, and browser WebRTC. It does not substitute the Realtime API or dictation. The application server exchanges the browser SDP through `POST /v1/live/sessions`; the provider response supplies `session.id` and `transport.sdp`. The server attaches to `/v1/live/sessions/{session_id}/attach` before returning the answer SDP. Project credentials remain server-side, loaded from the private runtime environment. Sessions explicitly set `store:false`; no reflected raw audio is persisted. This disables optional Live recording storage, not every provider retention policy.

The API is grounded in the official [WebRTC guide](https://developers.openai.com/api/docs/guides/voice-webrtc?api=live), [client delegation contract](https://developers.openai.com/api/docs/guides/live-delegation), [server controls](https://developers.openai.com/api/docs/guides/voice-server-controls?api=live), and [session lifecycle](https://developers.openai.com/api/docs/guides/live-conversations). OpenAI documentation was fetched on September 11, 2026. Live and Realtime schemas differ; there is no Realtime `call_id`, `response.create`, or fabricated audio-cancel event in this client-delegation adapter.

## Application boundary

`POST /api/v1/voice/sessions` accepts `{conversation_id, context_version, sdp, idempotency_key}` and returns `{id, provider_session_id, sdp, status, max_duration_seconds}`. `GET /api/v1/voice/sessions/{id}` returns the owned snapshot; `GET /api/v1/voice/sessions` lists the latest twenty owned attempts. `POST /api/v1/voice/sessions/{id}/close` ends voice. A snapshot includes `controller_connected`, `playback_blocked`, `revision`, `last_run_id`, `usage_seconds`, `final_usage_confirmed`, and a content-free error code.

Creation is persisted before the provider request. Same owner/key/body returns the same connected session; changed content conflicts. Unknown creation outcomes are recorded and block another attempt. They are never silently rebilled. An unknown provider session cannot be declared closed merely by clicking End; maintainers must reconcile the attempt. Admission permits two potential active voice sessions globally, one per anonymous owner, four starts per owner per ten minutes, and a five-minute session duration. These are reliability limits, not a custom billing dashboard.

The sideband owns transcript ingestion and delegation. Browser captions do not authorize work. Provider transcript fragments retain their original text and timestamps; the provider has no authoritative turn-completed transcript event. Delegation metadata identifies work but contains no question. A bounded OpenRouter intent-resolution request reads server-observed fragments and selected context, applies corrections, and asks for clarification when needed. Its actual usage is retained in the delegation record. Unknown identifiers or newly introduced numeric details are rejected before the normal source lookup. Final answers use the same persisted run and evidence pipeline as typed input.

Structured OpenRouter calls also create a durable `ProviderAttempt` before network dispatch. Each successful or failed response retains its own known usage independently of later stages. Cancellation or timeout without a receipt records usage as unknown, never zero. Receipt writes finish within a bounded, cancellation-shielded task; an unavailable receipt store leaves the dispatch unresolved and prevents reporting a fully persisted success. Run metrics and delegation records may copy the same usage, so billing summaries must count the attempt ledger once. Raw request/response bodies, prompts, transcripts, and keys are not stored in that ledger.

Postgres stores unique provider event IDs and payloads, unique session/delegation identities, current delegation revisions, earlier revision/run mappings, and session snapshots. A current controller owner, expiring lease, and monotonically increasing fence control mutations and playback commands. Local correction revisions suppress obsolete results; explicit correction language immediately blocks playback and retains one latest pending revised intent. Only one answer execution slot runs. Cancellation waits for its persisted run to release the slot before replacement work can proceed. A stalled cancellation or lost sideband closes the session rather than launching parallel replacement work.

End stops media at the browser and initiates bounded server cleanup. Already requested application work may finish and persist without speaking afterward. Reset, expired ownership, and context changes cancel affected voice work. The server waits for `session.closed` before treating final usage as confirmed; cumulative `usage.seconds` snapshots are replaced, never summed. Hangup success or socket closure alone is not final usage proof.

If neither the close event nor hangup confirms termination, the controller remains `closing` with a cleanup-only lease. It makes one early hangup retry and a final attempt at the original session deadline. Continued failure is retained as `uncertain`, blocks replacement sessions and is shown honestly in the browser. A known provider session can be reconciled through its owned close endpoint when service access returns; a session with an unknown provider ID cannot be declared closed. No-controller recovery and process shutdown preserve this uncertainty too. Each newly prepared browser SDP has its own attempt key, and End during offer preparation prevents provider dispatch.

## Verified so far

The bounded real-provider probe in `2026-09-11-live-capability/probe.json` (retained in the private development archive) started `gpt-live-1` over its primary WebSocket and immediately closed it. OpenAI emitted `session.started` and `session.closed` with `close_requested`, `store:false`, and final duration `0.0` seconds. This is account/model startup and finalization evidence only. The probe used no physical microphone and did not test speech, listening, WebRTC, delegation, or deployment.

`uv run pytest -q apps/api/tests/test_voice.py apps/api/tests/test_voice_postgres.py` passed 16 tests on September 11, 2026: provider schema and no retry after uncertain creation; transcript/delegation deduplication; missing-transcript clarification; correction and stale-result suppression; out-of-order delegation; sideband failure; cumulative usage and raw-audio omission; End preserving requested work; answer timeout; bounded appends; persisted admission/idempotency; cross-owner rejection; uncertain creation blocking; concurrent Postgres delegation claims and revisions; expired-owner rejection; and recovery that does not interrupt a renewed lease. The Postgres tests use isolated temporary databases and declared provider doubles. They do not establish spoken correctness.

The later `live-integration-review-20260911/results.json` (retained in the private development archive) passed 21 focused backend tests and all 24 frontend tests, plus the production frontend build. Added regressions cover reconnect after a recorded failure, cancellation before offer dispatch, unconfirmed cleanup disclosure, bounded cleanup retries, uncertainty blocking/reconciliation, and cleanup leases after owner reset or failed controller startup. These checks still use provider/media doubles and isolated Postgres; no additional paid request or spoken acceptance is implied.

## Acceptance still pending

The current path lets GPT Live paraphrase checked factual text. Server instructions can redirect speech but cannot guarantee that already queued WebRTC audio stopped. `playback_blocked` and client muting are controls to test, not proof of heard-audio correctness. Instruction or commentary acknowledgments never authorize resuming stale audio on their own. Native-versus-controlled playback selection remains dependent on actual audio trials.

Required remaining evidence includes an actual browser WebRTC journey; verified delegation through the selected generation provider; 12 frozen Live scenario families with three trials for each final voice path compared; actual audio, captions, and backend-result inspection separately; correction during lookup, speech, and reconnect; pauses, background speech, identifier and 24/48-hour cases; omitted prices and dates; failed retrieval; sideband loss while media remains connected; browser autoplay/permission recovery; and physical microphone/listening checks on the final deployed URL. Synthetic microphone fixtures must be labeled separately. The Live gate and final ready-to-use claim remain pending until these checks pass.
